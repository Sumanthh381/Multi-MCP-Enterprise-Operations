# Design decisions

1. **Official MCP SDK, stdio transport.** Each domain is a separate process with real initialization, discovery and typed invocation. Local process ownership keeps the demonstration simple; production remote servers should use MCP streamable HTTP with authenticated identities.
2. **Two source domains.** The alarm MCP server uses authenticated HTTP to the complete simulator. Work-order MCP uses persisted SQLite maintenance history and draft/approval operations. This satisfies cross-domain discovery and chaining without requiring GitHub API credentials during evaluation.
3. **Explicit intent planning and extractive generation.** A bounded vocabulary supports multiple assets, time ranges, analytics and follow-ups rather than hard-coding sample responses. It is deterministic and reproducible without an LLM key. This is not unrestricted natural-language reasoning; a provider interface with schema-constrained planning is a future extension, not an implemented feature.
4. **Sparse hybrid retrieval.** TF-IDF cosine plus lexical coverage gives inspectable vector retrieval over a small corpus. JSON content and hashes avoid serialized executable artifacts. No external vector service is needed.
5. **Separate proposal from action.** Preparing a draft creates no ticket. Confirmation validates conversation ownership and is idempotent. Actual GitHub issues are not created by the application; tickets are deliberately local mocks.
6. **Failures remain visible.** Required source failure stops analysis; optional source failure preserves partial results. Timelines carry the same trace as the source API. Retrying reads and read-like calculations is safe; ticket writes are not automatically retried.
7. **Packaging follows process ownership.** Compose has two services; the backend owns MCP subprocess startup/shutdown. Health checks ensure the simulator is healthy first. The local launcher mirrors this topology.
8. **Honest test evidence.** Tests cover real protocols and retrieval, and reports are generated by actual runs. Tests were added alongside implementation; no claim of a strict red/green TDD history is made. Coverage distinguishes executed lines from unmeasured subprocesses.
